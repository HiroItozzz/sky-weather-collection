# 設計メモ

空の写真と撮影時のメタデータを集めてデータセットを作り、「空の様子から少し先の天気」を予測するモデルを学習するためのプロジェクト。

このメモは、2026-10 に行った設計の議論（気象・ML、アプリ、サーバー、懐疑役の4つの観点）の結論をまとめたもの。未決の事項は最後の節に挙げる。

## 1. 目標と成功の基準

- 予測対象は当面「撮影地点で、撮影から60分以内に降水があるか」の2値分類とする。
- 目標は天気APIの予報に勝つことではない。「天気APIの現在値に画像を加えると、予測が良くなるか」を確かめることを目標にする。
- 比較対象
  1. 気候値（その時期・場所でふだん雨が降る割合）
  2. 持続予報（今降っていれば1時間後も降る）
  3. 天気APIの値だけを使ったモデル
  4. 人間の予想（後述の予想ゲームで集めた回答）
- 指標は Brier スコアと PR-AUC を使う。日単位のブートストラップで信頼区間を出す。
- 評価は次の2本立てにする。
  - 未来の日付で当たるか：日付単位で、撮影者全員分をまとめて分割する。同じ日の写真は場所が違っても同じ気象場（前線や低気圧の配置）を共有しているので、ランダムに分割すると正解が漏れる。
  - 知らない人の写真で当たるか：撮影者単位で分割する。
- 夜間（太陽高度が一定値未満）の写真は対象外とする。

## 2. 学習の方針（データが溜まってから着手）

- 集まる枚数は、1人あたり年に数百枚程度と見込む。この量では画像モデルを一から学習できない。
- そこで、学習済みの画像モデル（CLIP、DINOv2 など）の重みは固定して埋め込みを取り出し、その上にロジスティック回帰や GBDT などの小さなモデルを載せる。
- 画像が本当に効いているかは、次の方法で確かめる。
  - 画像特徴を別の写真のものとシャッフルし、精度の差が消えるかを見る。
  - 簡単な画像統計（明るさ、青の比率など）だけのモデルと比べる。
  - 画像の埋め込みから撮影者や機種を当てられるか試す。当てられるなら、モデルが天気ではなく機種の色の癖を覚えている可能性がある。

## 3. 全体構成

```
[スマホアプリ] --HTTPS--> [Cloud Run: FastAPI]
                              |-- Cloud Storage : 画像、天気APIの生レスポンス
                              |-- Firestore     : 撮影者、観測（メタデータ）、ジョブの状態
                              `-- Cloud Tasks   : 天気データの取得を予約
                                       |
                                       v
                              [Open-Meteo / アメダス]
```

- サーバーは GCP 上に置く（ユーザーが gcloud に慣れているため）。
- Cloud Run はコンテナを使い捨てにするので、SQLite のようにファイルに書く DB は使わない。メタデータは Firestore に、画像と生レスポンスは Cloud Storage に保存する。
- Cloud SQL は月額費用がかかるため使わない。
- 個人規模であれば、ほぼ無料枠に収まる見込み（推測。運用を始めたら請求額を確認する）。

## 4. 撮影時に記録するメタデータ（schema_version 1）

取れなかった項目は 0 ではなく null にする。値が 0 なのか取れなかったのかを区別するため。

| 項目 | 内容 |
|---|---|
| `schema_version` | 1 |
| `observation_id` | 端末で生成した UUID。再送したときの重複判定に使う |
| `captured_at` | 撮影時刻（UTC、ミリ秒まで） |
| `tz_offset_min` | 端末のタイムゾーンの UTC からのずれ（分） |
| `location` | `lat`, `lon`, `accuracy_m`, `altitude_m`, `fix_time`（位置を取得した時刻） |
| `orientation` | `azimuth_deg`（真北基準）, `pitch_deg`（仰角）, `roll_deg`, `declination_deg`（磁北からの偏角）, `accuracy`, `stddev_deg`（シャッター前後0.5秒のばらつき） |
| `camera` | `focal_length_mm`, `focal_length_35mm`, `exposure_time_s`, `iso`, `f_number`, `white_balance`, `image_width`, `image_height` |
| `device` | `platform`（android / ios / web）, `os_version`, `model`, `app_version` |
| `capture_path` | 撮影の経路（native / web） |
| `user_guess` | 予想ゲームの回答（降る / 降らない / 未回答） |
| `image_sha256` | 転送中の破損を検出するためのハッシュ |

- `location.altitude_m` は WGS84 楕円体からの高さ（Android の `Location.getAltitude()` の値）をそのまま記録する。海抜ではない（日本ではおよそ 30〜40m 大きい）。高度の精度が取れないときは null。
- 姿勢は方位角・仰角・ロールの3つで一通りに決まる（カメラが真上・真下のときの約束は `docs/m2-app-sensors.md` の 3.3 節）。四元数や回転行列は記録しない。
- 太陽の高度と方位は、時刻と位置から計算できる。保存時に計算して添えておく。
- 方位角は回転行列から直接計算する。オイラー角は真上付近や端末を立てたときに不安定になるので使わない。

## 5. 天気データ（特徴量とラベル）

天気データの取得は、撮影1件につき2回に分ける。

| 取得するタイミング | 用途 | 取得する範囲 |
|---|---|---|
| アップロード直後 | 特徴量（撮影時点でわかっていた情報だけ） | Open-Meteo の予報（`jma_msm`、`jma_seamless`、`best_match`） |
| `ceil_hour(t+3h)` の3時間後（6〜7時間後） | ラベル（実際に起きたこと） | Open-Meteo の値（t-3h〜t+3h の1時間値、t-1h〜t+2h の15分値）、アメダスの最寄り3地点の10分値（t-1h〜t+3h） |

- ラベルの取得は、撮影から6〜7時間後に行う。取得する範囲の終わり（1時間値なら `ceil_hour(t+3h)`）を過ぎてから、さらに3時間待つ。理由は2つある。
  - 範囲の終わりより前に取得すると、最後の行がまだ予報値になってしまう。
  - Open-Meteo の「過去」の値は、その時点で最新のモデル実行の結果から来る。JMA の MSM は数時間おきに更新されて公開も遅れるので、待つほど実況に近い値になる。
- 取得した範囲の終わりが取得時刻より後になっていたら、その取得は完了にせず再試行する。この条件はラベル用の取得に適用する（特徴量用は予報を取るのが目的なので、範囲の終わりが未来になるのが当然）。
- アメダスで、ある観測点のファイルがすべて 404 のときは、取得を失敗として扱う。黙って空のラベルで完了にはしない。
- 取得する変数は、降水量、weather_code、雲量（全体・下層・中層・上層）、気温、露点、湿度、海面気圧、風向・風速、CAPE、短波放射、視程。
- レスポンスは gzip にしてすべて Cloud Storage に保存する。1件あたり 50KB 未満の見込み（推測）。生レスポンスを残しておけば、ラベルの定義を変えたくなったときに、API を呼び直さずに作り直せる。
- ラベル用の値はすべて「撮影地点の正確な座標」で取得する。外部の API に渡す座標は小数第2位（約1km）に丸める。
- アメダスの観測点は約17km 間隔なので、局地的なにわか雨を取りこぼすことがある。観測点との距離も一緒に保存する。
- アメダスのデータは、気象庁サイトが内部で使っている JSON から取る。公式の API ではないため、1件につき数回程度の低頻度にとどめる。
- 気象庁のナウキャストやレーダーのタイルは、規約がはっきりしないので自動では取得しない。

## 6. スマホアプリ

- Expo（React Native、TypeScript）で作る。1つのコードで Android と iOS の両方に出せて、Mac がなくても EAS Build で iOS 版をビルドできるため。
- 最初は Android だけで動かす。ストアでの公開も Android（Google Play）から始める。iOS は Apple Developer Program に加入してから対応する。
- Expo では端末の向きの精度を検証する必要がある（M2）。足りなければ、その部分だけネイティブのモジュール（Kotlin）を書いて組み込む。
- 検討して採らなかった方式：Kotlin のみ（iOS 版を Swift で書き直すことになり、Mac も必要）、Web アプリ（カメラの情報が取れず、iOS では端末に保存したデータが消えることがある）、Flutter（Dart を新たに学ぶ必要があり、向きを取るプラグインも弱い）。

アプリの方式にかかわらず、次の点は共通にする。

- 撮影したら、まず端末内に画像とメタデータの JSON を保存する。送信が成功するまで、この保存分を消さない。
- 通信できないときは端末内に溜めておき、電波が戻ったときかアプリを開いたときに再送する。
- 地上がほとんど写らないように、仰角が一定値（例：20°）以上のときだけシャッターを押せるようにする。
- 方位の精度が低いときは、端末を8の字に振るキャリブレーションを促す。

## 7. API

- `PUT /v1/observations/{observation_id}`
  - multipart 形式で、`metadata`（JSON）と `image`（JPEG）を送る。
  - 新規なら 201、同じ内容がすでにあれば 200、同じ ID で中身が違えば 409 を返す。
- `GET /v1/observations/{observation_id}`：端末が、送信済みかどうかを確認するために使う。
- `POST /internal/tasks/fetch-weather`：Cloud Tasks から呼ばれる。OIDC で認証する。
- `GET /healthz`：死活確認用。

### 認証

- 撮影者ごとに長いランダムな招待コードを発行して渡し、アプリに一度入力してもらう。
- アプリは `Authorization: Bearer <コード>` を付けて送る。
- サーバーにはコードのハッシュだけを保存する。端末をなくしたときは、そのコードを無効にする。
- ストアで公開する段階になったら、招待コードなしで登録できる方式に切り替える（8節を参照）。

## 8. プライバシーと公開

- サーバーには正確な値を保存する。データセットを公開するときは、別に「ぼかしたコピー」を作る。
- 公開版で行う処理
  - 位置は、固定の格子（例：0.05°）に丸める。写真ごとにランダムなノイズを足す方法は使わない。同じ場所の写真が多いと、平均を取るだけで元の位置が戻ってしまうため。
  - 撮影者が登録したプライバシーゾーン（自宅など）の周辺で撮った写真は、位置を消す。
  - 撮影者が k 人未満の格子は、粗い格子にまとめるか、公開版から除く。
  - 時刻は10分〜1時間単位に丸める。
  - EXIF は削除する。顔や車のナンバーが写った写真は、ぼかすか公開版から除く。
  - 撮影者 ID は、公開のたびに別のランダムな ID に付け替える。
- 最初から用意しておくもの（サーバー側は管理コマンドで先に用意し、アプリの画面は一般公開の前に作る）
  - 撮影者ごとの「公開データに含めてよいか」の同意フラグ
  - プライバシーゾーンの登録
  - 公開版には、天気APIの生レスポンスの封筒（アメダスの観測点までの距離を含む）を入れない。3つの観測点までの距離があれば、三点測位で撮影位置がかなり正確に戻ってしまうため。
  - 天気データの出典と取得日時の記録（Open-Meteo は CC BY 4.0、気象庁のデータは政府標準利用規約に従い、公開時に出典を明記する）

### 濫用への備え

- 撮影者ごとに、1日（UTC）に受け付ける観測の数に上限（既定 100 件）を設ける。超えたら 429 を返す。招待コードが漏れたときの被害（保存の費用、外部 API の呼び出し）を抑えるため。
- アップロードは、本文を読む前に大きさ（Content-Length）と招待コードを確かめる。未認証のリクエストにサーバーの資源を使わせないため。
- 撮影者のデータ（観測、画像、天気データ）をまとめて消す管理コマンドを用意する。ストアでの公開時のデータ削除の依頼に応えるため。

### ストアでの公開を見据えて

まとまった量のデータを集めるには、いずれストアでの公開が必要になる。そのときに必要になるもの：

- Google Play の開発者登録（1回のみの支払い）と Apple Developer Program（年額）
- プライバシーポリシー、データ収集の内容の申告、利用目的の同意画面
- 撮影者からのデータ削除の依頼に応じる仕組み
- 招待コードに代わる登録方式（初回起動時に匿名アカウントを発行する、など）

## 9. 収集を続けてもらうための仕掛け

ストアで公開するなら、使う人にとってのメリットや楽しさが欠かせない。初期は次の3つを入れる。どれもモデルがなくても成り立つ。

1. **撮影直後の天気表示**：撮影したら、現在の天気APIの値を表示する。
2. **予想ゲーム**：撮影時に「1時間後に降るか」を答えてもらい、ラベルが付いたら答え合わせをして的中率を見せる。回答は人間の予想として、モデルの比較対象にもなる。
3. **貢献の見える化**：「あなたの写真が N 枚データセットに入った」と見せる。あわせて「曇りや雨の日の写真は特に貴重」と伝える。

3 は、2 で生まれる「雨が降りそうなときだけ撮る」偏りを打ち消すために入れる（降らなかった報告にも価値があるとする CoCoRaHS と同じ考え方）。過去に撮った写真のタイムラインも、軽いので入れてよい。

モデルができた後は、予想ゲームを「本人・天気API・空のAI」の3者の答え合わせに広げる。

### やらないこと

- 撮影者どうしで写真を見せ合う機能（空マップなど）。映える空ばかり集まるうえに、プライバシー対策と投稿のチェックが重い。
- 「いいね」の数、投稿数のランキング、珍しい空へのごほうび、ガチャや課金。データが偏る。
- 1日2回以上の通知、連続記録（ストリーク）で圧をかけること。リマインダーは1日1回まで。ランダムな時刻に通知して「ふつうの空」も撮ってもらう。
- 空のAIの予測を「予報」として出すこと。日本では予報業務に気象業務法の許可が要る（要確認）ため、「参考」や「答え合わせ」の扱いにとどめる。

## 12. M1 の仕様：アップロード API（ローカル版）

M1 では、7節の API のうち天気データの取得以外を、ローカルで動く形で作る。GCP のサービス（Firestore、Cloud Storage、Cloud Tasks）は M4 で対応する。そのときに差し替えられるよう、保存先はインターフェースで分けておく。

### 構成

- `server/` に置く。Python 3.13、パッケージ管理は uv。
- 依存パッケージ：fastapi、uvicorn、pydantic v2、python-multipart。開発用に pytest、httpx、ruff。
- パッケージ名は `sky_server`。
- 保存先のインターフェース
  - `ObservationRepository`：撮影者と観測（メタデータ）の保存。M1 ではローカル版を作る（JSON ファイル。1件1ファイル）。
  - `BlobStore`：画像の保存。M1 ではローカルのディレクトリ版を作る。
  - データの置き場所は、環境変数 `SKY_DATA_DIR` で指定する。
- 写真は元の画像のまま（EXIF 付き）保存する。EXIF を消すのは公開版を作るときだけ。

### 撮影者と招待コード

- 撮影者のデータ：`user_id`（UUID）、`name`、`token_hash`、`created_at`、`revoked_at`（null なら有効）、`consent_public`（初期値 false）。
- 招待コードは `secrets.token_urlsafe(32)` で生成する。サーバーには SHA-256 のハッシュ（16進数）だけを保存する。コードは十分に長いランダムな文字列なので、パスワード用の遅いハッシュは不要。
- 管理用のコマンド：`uv run python -m sky_server.admin create-user --name <名前>` で撮影者を作り、コードを1回だけ表示する。`revoke-user --user-id <ID>` で無効にする。
- 認証の失敗（ヘッダーがない、コードが違う、無効にされた）はすべて 401 を返す。

### `PUT /v1/observations/{observation_id}`

- `observation_id` は UUID の形式（大文字小文字は問わず、小文字に正規化して扱う）。形式が違えば 422。
- multipart のパート：`metadata`（JSON 文字列）、`image`（`image/jpeg`）。
- metadata は4節の項目を pydantic で検証する。検証に失敗したら 422。
  - `schema_version` は 1 のみ受け付ける。
  - `observation_id` はパスの ID と一致しなければならない。
  - `captured_at` はタイムゾーン付きの時刻にする。サーバー時刻より10分以上未来なら 422。
  - 値の範囲：`lat` -90〜90、`lon` -180〜180、`azimuth_deg` 0 以上 360 未満、`pitch_deg` -90〜90、`roll_deg` -180〜180、`accuracy_m` 0 以上。
  - `orientation.accuracy` は `high` / `medium` / `low` / `unreliable` / null。
  - `device.platform` は `android` / `ios` / `web`。`capture_path` は `native` / `web`。
  - `user_guess` は `rain` / `no_rain` / null。
  - 4節で null を許す項目：`location.altitude_m`、`orientation` の各値、`camera` の各値、`user_guess`。`location` と `orientation` そのものも null を許す。
  - 知らない項目が来たら 422 にする（つづりの間違いに気づくため）。
- 画像の大きさの上限は 10MB。超えたら 413。
- 受け取った画像の SHA-256 が `image_sha256` と一致しなければ 422。
- 重複の扱い
  - 同じ ID で、同じ撮影者・同じ `image_sha256` の観測がすでにあれば、何も変えずに 200 を返す（再送とみなす）。
  - 同じ ID で、撮影者か `image_sha256` が違えば 409。
  - 新規なら保存して 201。
- サーバーが付け加えて保存する項目：`user_id`、`received_at`（UTC）、`image_key`。
- 画像のキーは `{observation_id}/{image_sha256}.jpg` にする。同じ ID で別の画像が同時に届いても、互いに上書きしないようにするため。
- 応答の本文：`{"observation_id": "...", "status": "created"}`（200 のときは `"exists"`）。

### `GET /v1/observations/{observation_id}`

- 自分の観測なら `{"observation_id": "...", "received_at": "..."}` を返す。
- 存在しないとき、または他人の観測のときは、どちらも 404 を返す（他人の ID が存在するかどうかを漏らさないため）。

### `GET /healthz`

- 認証なしで `{"status": "ok"}` を返す。

### 完成条件

- `cd server && uv run pytest` がすべて通る。
- `uv run ruff check` と `uv run ruff format --check` が通る。
- 上に挙げた応答コードのそれぞれについて、テストがある（201、再送の 200、409 が2通り、401 が3通り、413、422（ハッシュの不一致、ID の不一致、範囲外の値、知らない項目））。また、GET で他人の観測が 404 になることのテストもある。
- `server/README.md` に、ローカルでの起動方法、撮影者の作り方、curl でアップロードを試す例を書く。

## 13. M5 の仕様：予想ゲーム、撮影直後の天気表示、貢献の見える化

9節の3つの仕掛けを作る。サーバーは、天気データの生レスポンスから表示用の小さな要約を作って返す。アプリは、それを画面に出す。

### 13.1 予想の回答

- 撮影画面に「1時間後に降る / 降らない / わからない」の切り替えを置き、シャッターを押す**前に**選んでもらう。初期値は「わからない」（`user_guess: null`）。
- 撮った後に選ぶ方式にしない。撮影から保存までの間が空くと、その間にアプリが終了して写真を失うおそれがあるため。また、撮影後に天気を見てから答えを変えられないようにするため。
- 回答は、今までどおりメタデータの `user_guess` に入れて送る。

### 13.2 答え合わせの定義（ゲーム用の暫定版）

学習用のラベルの定義は、データが溜まってから別に決める。ここで決めるのは、ゲームの答え合わせに使う定義だけ。

- 対象は、撮影時刻 t から t+60分までの間（t は含まず、t+60分は含む）。
- 撮影地点から 10km 以内にアメダスの観測点があり、その観測点の10分値が対象の時間帯に欠けずにそろっていれば、それを使う。どれか1つでも降水量が 0 より大きければ `rain`、すべて 0 なら `no_rain`。
- そうでなければ、Open-Meteo の15分値（`jma_seamless`）を使う。対象の時間帯の降水量の合計が 0.1mm 以上なら `rain`、それ未満なら `no_rain`。
- `label` のジョブが完了していない、または両方とも値がそろわないときは `unknown`。
- どの方法で判定したか（`amedas` / `open_meteo` / null）も返す。

### 13.3 撮影時の天気

- `forecast` のジョブで取った Open-Meteo の値（`jma_seamless`）から、撮影時刻を含む1時間の値を取り出す：`weather_code`、`temperature_2m`、`precipitation`、`cloud_cover`。
- `weather_code` は、次の3つに分類した `category` も返す：`clear`（0〜2）、`cloudy`（3、45、48）、`rain`（51 以上）。
- `forecast` のジョブが完了していなければ null。

### 13.4 要約の保存

- ジョブが `done` になったときに、13.2・13.3 の結果を計算してジョブの状態に `summary` として保存する。API を呼ぶたびに gzip の生レスポンスを読み直さないため。
- 要約の計算に失敗しても、ジョブは `done` のままにする（生レスポンスは保存できているので、あとで作り直せる）。要約は null にして、エラーをログに出す。
- 要約の計算は、生レスポンスから何度でも作り直せる純粋な関数にする。管理コマンドで、全件の要約を作り直せるようにする。

### 13.5 API

すべて招待コードの認証が必要。自分の観測だけを返す。

- `GET /v1/observations/{observation_id}`（項目を追加）
  ```json
  {
    "observation_id": "...",
    "received_at": "...",
    "captured_at": "...",
    "user_guess": "rain",
    "weather_at_capture": {"category": "cloudy", "weather_code": 3, "temperature_c": 18.2, "precipitation_mm": 0.0, "cloud_cover_pct": 90} ,
    "answer": {"result": "rain", "source": "amedas"},
    "correct": true
  }
  ```
  - `weather_at_capture` は 13.3 が null なら null。
  - `answer.result` は `rain` / `no_rain` / `unknown`。`correct` は、`user_guess` が null か `answer.result` が `unknown` なら null。
- `GET /v1/me/observations?limit=50&before=<captured_at>`
  - 自分の観測を `captured_at` の新しい順に返す。項目は上の GET と同じ。`limit` は 1〜100（既定 50）。
  - 応答は `{"observations": [...], "next_before": "<captured_at>" | null}`。次のページがなければ `next_before` は null。
  - Firestore では `user_id` と `captured_at` の複合インデックスが必要になる。デプロイ手順書に追記する。
- `GET /v1/me/stats`
  ```json
  {
    "observations_total": 42,
    "answered_total": 30,
    "guesses_total": 20,
    "guesses_correct": 14,
    "by_category": {"clear": 20, "cloudy": 15, "rain": 5, "unknown": 2}
  }
  ```
  - `answered_total` は `answer.result` が `unknown` でない観測の数。`guesses_*` は、`user_guess` があり、かつ答えが出たものだけを数える。`by_category` は撮影時の天気の分類ごとの数。
  - 個人規模なので、M5 では全件を読んで数える。件数が増えたら、集計値を別に持つ方式に変える。

### 13.6 アプリの画面

- **撮影画面**：予想の切り替え（13.1）。保存したら「保存しました」に加えて、送信が済んで `weather_at_capture` が取れ次第、撮影時の天気を表示する（取れなければ何も出さない。最大1分ほど問い合わせる）。
- **タイムライン画面**：`GET /v1/me/observations` の一覧。サムネイル、撮影日時、予想、答え、当たりかどうか、撮影時の天気。答えが `unknown` の間は「答え合わせ待ち（撮影の約6〜7時間後）」と出す。
  - サムネイルは、送信が成功して元の画像を消すときに、長い辺 320px 程度の縮小版を端末内に残して使う。サーバーから画像は取得しない。
- **記録画面（貢献の見える化）**：`GET /v1/me/stats` を表示する。送った枚数、予想の的中率、天気の分類ごとの枚数。曇りと雨の写真が少なければ「曇りや雨の日の写真は特に貴重です」と添える。
- 通信できないときは、最後に取得した内容を表示する。
