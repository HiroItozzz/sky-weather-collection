# 設計メモ

空の写真と撮影時のメタデータを集めてデータセットを作り、「空の様子から少し先の天気」を予測するモデルを学習するためのプロジェクト。

このメモは、2026-10 に行った設計の議論（気象・ML、アプリ、サーバー、懐疑役の4つの観点）の結論をまとめたもの。未決の事項は最後の節に挙げる。

## 1. 目標と成功の基準

- 予測対象は当面「撮影地点で、撮影から60分以内に降水があるか」の2値分類とする。
- 目標は天気APIの予報に勝つことではない。「天気APIの現在値に画像を加えると、予測が良くなるか」を確かめることを目標にする。
- 比較対象
  1. 気候値（その時期・場所でふだん雨が降る割合）
  2. 持続予報（今降っていれば1時間後も降る）
  3. 天気APIの値だけを使ったモデル
  4. 人間の予想（後述の予想ゲームで集めた回答）
- 指標は Brier スコアと PR-AUC を使う。日単位のブートストラップで信頼区間を出す。
- 評価は次の2本立てにする。
  - 未来の日付で当たるか：日付単位で、撮影者全員分をまとめて分割する。同じ日の写真は場所が違っても同じ気象場（前線や低気圧の配置）を共有しているので、ランダムに分割すると正解が漏れる。
  - 知らない人の写真で当たるか：撮影者単位で分割する。
- 夜間（太陽高度が一定値未満）の写真は対象外とする。

## 2. 学習の方針（データが溜まってから着手）

- 集まる枚数は、1人あたり年に数百枚程度と見込む。この量では画像モデルを一から学習できない。
- そこで、学習済みの画像モデル（CLIP、DINOv2 など）の重みは固定して埋め込みを取り出し、その上にロジスティック回帰や GBDT などの小さなモデルを載せる。
- 画像が本当に効いているかは、次の方法で確かめる。
  - 画像特徴を別の写真のものとシャッフルし、精度の差が消えるかを見る。
  - 簡単な画像統計（明るさ、青の比率など）だけのモデルと比べる。
  - 画像の埋め込みから撮影者や機種を当てられるか試す。当てられるなら、モデルが天気ではなく機種の色の癖を覚えている可能性がある。

## 3. 全体構成

```
[スマホアプリ] --HTTPS--> [Cloud Run: FastAPI]
                              |-- Cloud Storage : 画像、天気APIの生レスポンス
                              |-- Firestore     : 撮影者、観測（メタデータ）、ジョブの状態
                              `-- Cloud Tasks   : 天気データの取得を予約
                                       |
                                       v
                              [Open-Meteo / アメダス]
```

- サーバーは GCP 上に置く（ユーザーが gcloud に慣れているため）。
- Cloud Run はコンテナを使い捨てにするので、SQLite のようにファイルに書く DB は使わない。メタデータは Firestore に、画像と生レスポンスは Cloud Storage に保存する。
- Cloud SQL は月額費用がかかるため使わない。
- 個人規模であれば、ほぼ無料枠に収まる見込み（推測。運用を始めたら請求額を確認する）。

## 4. 撮影時に記録するメタデータ（schema_version 1）

取れなかった項目は 0 ではなく null にする。値が 0 なのか取れなかったのかを区別するため。

| 項目 | 内容 |
|---|---|
| `schema_version` | 1 |
| `observation_id` | 端末で生成した UUID。再送したときの重複判定に使う |
| `captured_at` | 撮影時刻（UTC、ミリ秒まで） |
| `tz_offset_min` | 端末のタイムゾーンの UTC からのずれ（分） |
| `location` | `lat`, `lon`, `accuracy_m`, `altitude_m`, `fix_time`（位置を取得した時刻） |
| `orientation` | `azimuth_deg`（真北基準）, `pitch_deg`（仰角）, `roll_deg`, `declination_deg`（磁北からの偏角）, `accuracy`, `stddev_deg`（シャッター前後0.5秒のばらつき） |
| `camera` | `focal_length_mm`, `focal_length_35mm`, `exposure_time_s`, `iso`, `f_number`, `white_balance`, `image_width`, `image_height` |
| `device` | `platform`（android / ios / web）, `os_version`, `model`, `app_version` |
| `capture_path` | 撮影の経路（native / web） |
| `user_guess` | 予想ゲームの回答（降る / 降らない / 未回答） |
| `image_sha256` | 転送中の破損を検出するためのハッシュ |

- 太陽の高度と方位は、時刻と位置から計算できる。保存時に計算して添えておく。
- 方位角は回転行列から直接計算する。オイラー角は真上付近や端末を立てたときに不安定になるので使わない。

## 5. 天気データ（特徴量とラベル）

天気データの取得は、撮影1件につき2回に分ける。

| 取得するタイミング | 用途 | 取得する範囲 |
|---|---|---|
| アップロード直後 | 特徴量（撮影時点でわかっていた情報だけ） | Open-Meteo の予報（`jma_msm`、`jma_seamless`、`best_match`） |
| 撮影の3時間後＋余裕 | ラベル（実際に起きたこと） | Open-Meteo の値（t-3h〜t+3h の1時間値、t-1h〜t+2h の15分値）、アメダスの最寄り3地点の10分値（t-1h〜t+3h） |

- 取得する変数は、降水量、weather_code、雲量（全体・下層・中層・上層）、気温、露点、湿度、海面気圧、風向・風速、CAPE、短波放射、視程。
- レスポンスは gzip にしてすべて Cloud Storage に保存する。1件あたり 50KB 未満の見込み（推測）。生レスポンスを残しておけば、ラベルの定義を変えたくなったときに、API を呼び直さずに作り直せる。
- ラベル用の値はすべて「撮影地点の正確な座標」で取得する。外部の API に渡す座標は小数第2位（約1km）に丸める。
- アメダスの観測点は約17km 間隔なので、局地的なにわか雨を取りこぼすことがある。観測点との距離も一緒に保存する。
- アメダスのデータは、気象庁サイトが内部で使っている JSON から取る。公式の API ではないため、1件につき数回程度の低頻度にとどめる。
- 気象庁のナウキャストやレーダーのタイルは、規約がはっきりしないので自動では取得しない。

## 6. スマホアプリ

**方式は未決。** 候補と比較は次のとおり。

| 方式 | 長所 | 短所 |
|---|---|---|
| Expo（React Native） | 1つのコード（TypeScript）で Android と iOS の両方に出せる。EXIF を取れる。Mac がなくても EAS Build で iOS 版をビルドできる | 端末の向きを取る精度は検証が必要。足りなければ、その部分だけネイティブのモジュールを書く |
| Kotlin（Android ネイティブ） | センサーやカメラを最も細かく扱える | iOS 版は Swift で書き直しになり、Mac が必要 |
| Web アプリ | URL を送るだけで配れて、費用は0円 | カメラの情報が取れない。iOS では端末に保存したデータが消えることがある |

アプリの方式にかかわらず、次の点は共通にする。

- 撮影したら、まず端末内に画像とメタデータの JSON を保存する。送信が成功するまで、この保存分を消さない。
- 通信できないときは端末内に溜めておき、電波が戻ったときかアプリを開いたときに再送する。
- 地上がほとんど写らないように、仰角が一定値（例：20°）以上のときだけシャッターを押せるようにする。
- 方位の精度が低いときは、端末を8の字に振るキャリブレーションを促す。

## 7. API

- `PUT /v1/observations/{observation_id}`
  - multipart 形式で、`metadata`（JSON）と `image`（JPEG）を送る。
  - 新規なら 201、同じ内容がすでにあれば 200、同じ ID で中身が違えば 409 を返す。
- `GET /v1/observations/{observation_id}`：端末が、送信済みかどうかを確認するために使う。
- `POST /internal/tasks/fetch-weather`：Cloud Tasks から呼ばれる。OIDC で認証する。
- `GET /healthz`：死活確認用。

### 認証

- 撮影者ごとに長いランダムな招待コードを発行して渡し、アプリに一度入力してもらう。
- アプリは `Authorization: Bearer <コード>` を付けて送る。
- サーバーにはコードのハッシュだけを保存する。端末をなくしたときは、そのコードを無効にする。
- ストアで公開する段階になったら、招待コードなしで登録できる方式に切り替える（8節を参照）。

## 8. プライバシーと公開

- サーバーには正確な値を保存する。データセットを公開するときは、別に「ぼかしたコピー」を作る。
- 公開版で行う処理
  - 位置は、固定の格子（例：0.05°）に丸める。写真ごとにランダムなノイズを足す方法は使わない。同じ場所の写真が多いと、平均を取るだけで元の位置が戻ってしまうため。
  - 撮影者が登録したプライバシーゾーン（自宅など）の周辺で撮った写真は、位置を消す。
  - 撮影者が k 人未満の格子は、粗い格子にまとめるか、公開版から除く。
  - 時刻は10分〜1時間単位に丸める。
  - EXIF は削除する。顔や車のナンバーが写った写真は、ぼかすか公開版から除く。
  - 撮影者 ID は、公開のたびに別のランダムな ID に付け替える。
- 最初から用意しておくもの
  - 撮影者ごとの「公開データに含めてよいか」の同意フラグ
  - プライバシーゾーンの登録
  - 天気データの出典と取得日時の記録（Open-Meteo は CC BY 4.0、気象庁のデータは政府標準利用規約に従い、公開時に出典を明記する）

### ストアでの公開を見据えて

まとまった量のデータを集めるには、いずれストアでの公開が必要になる。そのときに必要になるもの：

- Google Play の開発者登録（1回のみの支払い）と Apple Developer Program（年額）
- プライバシーポリシー、データ収集の内容の申告、利用目的の同意画面
- 撮影者からのデータ削除の依頼に応じる仕組み
- 招待コードに代わる登録方式（初回起動時に匿名アカウントを発行する、など）

## 9. 収集を続けてもらうための仕掛け

盛り込みすぎないよう、次の3つに絞る。

1. 撮影直後に、現在の天気APIの値を表示する。
2. 予想ゲーム：撮影時に「1時間後に降るか」を答えてもらい、ラベルが付いたら答え合わせをする。回答は人間の予想として、比較対象にもなる。
3. 過去に撮った写真のタイムライン。

撮影のリマインダーは1日1回までにする。ランダムな時刻に通知して「ふつうの空」も撮ってもらうと、珍しい空ばかりが集まる偏りを減らせる。
